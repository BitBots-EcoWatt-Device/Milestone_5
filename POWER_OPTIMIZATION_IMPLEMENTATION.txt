## 1. WiFi Light Sleep Mode (Primary Optimization)

**Implementation:**
```cpp
WiFi.setSleepMode(WIFI_LIGHT_SLEEP);
```

**Location:** setup() function in main.cpp

**How it works:**
- ESP8266 enters light sleep automatically during delay() calls
- CPU drops from 80MHz to minimal power mode
- WiFi connection stays alive (periodic beacon listening)
- Device wakes up on:
  * Timer interrupts (Ticker callbacks)
  * WiFi events (incoming data)
  * Serial input
  * Any external interrupt

**Power Savings:**
- Active mode: ~80-90 mA
- Light sleep mode: ~15 mA
- Expected reduction: 60-75% in average current consumption

**Benefits:**
✓ Simple one-line implementation
✓ No changes to existing code logic
✓ WiFi stays connected
✓ Timers continue to work
✓ No functionality loss

**Compatibility:**
✓ Works with Ticker timers
✓ Works with WiFi operations
✓ Works with Serial communication
✓ Compatible with all ESP8266 libraries

## 2. CPU Idle Optimization (Secondary Optimization)

**Implementation:**
Added `yield()` calls throughout code at strategic locations

**Locations:**
- Main loop (after delay)
- WiFi connection wait loops
- Time synchronization loops
- HTTP retry delays
- Sensor polling loops (between reads)

**How it works:**
- `yield()` allows ESP8266 to process background tasks
- WiFi stack maintenance
- Watchdog timer feeding
- System event processing
- Prevents blocking of critical operations

**Power Savings:**
- Minimal direct savings (~1-2%)
- Improved WiFi stability = fewer retries = less power
- Prevents WiFi disconnections that waste power reconnecting

**Benefits:**
✓ Improves system responsiveness
✓ Better WiFi connection stability
✓ Reduces retry overhead
✓ Smoother operation

================================================================================
HOW LIGHT SLEEP MODE WORKS
================================================================================

### Normal Operation Flow:
1. Timer interrupt fires (e.g., pollTicker)
2. ESP8266 wakes from light sleep instantly
3. ISR sets flag (pollPending = true)
4. Returns to light sleep
5. Main loop() wakes up
6. Checks flag, executes pollSensors()
7. Returns to loop()
8. Hits delay(100)
9. **ENTERS LIGHT SLEEP** automatically
10. Repeat

### During Light Sleep:
- CPU: Halted (no code execution)
- RAM: Powered (data preserved)
- WiFi: Periodic beacon listening (stays connected)
- Timers: Hardware timers still running
- RTC: Running
- GPIO: Can wake on interrupt

### Wake Sources:
✓ Ticker timer interrupts (pollTicker, uploadTicker, configRequestTicker)
✓ WiFi events (incoming packets)
✓ GPIO interrupts (if configured)
✓ Serial data arrival
✓ Watchdog timer

### What Continues Working:
✓ WiFi connection maintained
✓ Ticker callbacks fire on time
✓ Serial communication responsive
✓ All sensors and peripherals accessible
✓ Time tracking accurate

### What Changes:
- CPU not executing code during sleep
- Lower power consumption
- Slightly longer response to serial input (~few ms)
- No visible functional difference

### 1. setup() - Enable Light Sleep


### 2. loop() - Enhanced idle sleep
```cpp

yield();     // Allow background processing
```

### 3. WiFi Connection - Optimized waits
```cpp
// Added yield() in WiFi connection loop
while (WiFi.status() != WL_CONNECTED && wifi_timeout < 30) {
    delay(1000);  // Light sleep active
    Serial.print(".");
    wifi_timeout++;
    yield();  // NEW: Allow WiFi processing
}
```

### 4. Time Sync - Optimized waits
```cpp
// Added yield() in time sync loop
while (now < 8 * 3600 * 2 && sync_timeout < 10) {
    delay(1000);  // Light sleep active
    now = time(nullptr);
    sync_timeout++;
    yield();  // NEW: Allow background processing
}
```

### 5. HTTP Retry - Optimized backoff
```cpp
// Added yield() after retry delay
delay(backoffMs);  // Light sleep during backoff
yield();           // NEW: Allow WiFi processing
```

### 6. Config Retry - Optimized delay

### 7. Sensor Polling - CPU idle optimization

================================================================================
TROUBLESHOOTING
================================================================================

### Issue: Device seems unresponsive
**Cause:** Deep sleep might be enabled instead of light sleep
**Solution:** Verify WiFi.setSleepMode(WIFI_LIGHT_SLEEP) in code

### Issue: WiFi disconnections
**Cause:** Light sleep timing with poor signal
**Solution:** 
- Check WiFi signal strength (RSSI)
- Move closer to router
- Consider disabling sleep if RSSI < -75 dBm

### Issue: Timers not firing on time
**Cause:** Should not happen with light sleep
**Solution:** 
- Verify Ticker callbacks are IRAM_ATTR
- Check that onPollTimer, onUploadTimer are marked correctly

### Issue: Power consumption not improving
**Cause:** Light sleep not activating
**Solution:**
- Verify WiFi.setSleepMode() call in setup()
- Check Serial Monitor for "[POWER] Light Sleep Mode enabled" message
- Use power-detailed to see if Sleep Time increased

### Issue: Serial Monitor shows garbled text
**Cause:** Normal during sleep entry/exit with some monitors
**Solution:** Cosmetic only, no impact on functionality

================================================================================
TECHNICAL NOTES
================================================================================

### Why Light Sleep Instead of Deep Sleep?
- Light sleep keeps WiFi connected
- Ticker timers continue working
- No system restart needed
- Instant wake-up (microseconds)
- No state loss
- Much simpler implementation

### Why Not Modem Sleep?
- Modem sleep disconnects WiFi periodically
- Would require complex reconnection logic
- Upload timing becomes unpredictable
- Configuration updates could be missed
- Not worth the complexity for marginal additional savings

### ESP8266 Power Modes Summary:
| Mode | Current | WiFi | Timers | Wake Time | State |
|------|---------|------|--------|-----------|-------|
| Active | 80-90 mA | ✓ | ✓ | N/A | Full |
| Light Sleep | 15 mA | ✓ | ✓ | <3 ms | Full |
| Modem Sleep | 15-70 mA | Periodic | ✓ | <3 ms | Full |
| Deep Sleep | 20 μA | ✗ | ✗ | 100+ ms | Lost |

Light Sleep is the sweet spot for our use case!
